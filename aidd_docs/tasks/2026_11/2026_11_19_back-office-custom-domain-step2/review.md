### Phase 2 — Câblage CloudFront (pas de `plan.md` dédié)

> Aucun plan n'existe pour cette étape. Critères repris de la ligne `Decisions` de `aidd_docs/tasks/2026_11/2026_11_18_back-office-custom-domain/plan.md` qui définit le périmètre de la 2e PR, complétés par les 7 points de contrôle fournis à la revue.

- [x] `aws_acm_certificate_validation` ajouté avec `provider = aws.us_east_1` — `acm.tf:37-38`. Correct et obligatoire : le certificat est créé par `aws.us_east_1` (`acm.tf:2`) ; sans l'alias, la ressource interrogerait ACM en `eu-west-3` (`var.aws_app_region`, `providers.tf:16`) où le certificat n'existe pas.
- [x] `validation_record_fqdns` référence la même extraction que les outputs de l'étape 1 — `acm.tf:40` et `acm.tf:16` portent l'expression `tolist(aws_acm_certificate.BackOffice.domain_validation_options)[0].resource_record_name` au caractère près. Une seule extraction, pas de divergence possible entre ce que la CI affiche à l'utilisateur et ce que Terraform attend. Le certificat n'ayant qu'un `domain_name` et aucun SAN, l'index `[0]` couvre bien la totalité des options de validation.
- [x] `aliases = [var.back_office_domain]` par environnement, pas de valeur en dur — `s3_back-office.tf:43`. Résout à `back-office-stg.myhobbees.fr` (`environments/stg/variables.stg.tf:34`) et `back-office.myhobbees.fr` (`environments/prd/variables.prd.tf:34`), soit la même variable que celle qui alimente `domain_name` du certificat (`acm.tf:3`) — alias et certificat ne peuvent pas diverger.
- [x] `viewer_certificate` basculé sur le certificat validé — `s3_back-office.tf:89-93` : `acm_certificate_arn = aws_acm_certificate_validation.BackOffice.certificate_arn`, `ssl_support_method = "sni-only"`, `minimum_protocol_version = "TLSv1.2_2021"`. Le passage par `aws_acm_certificate_validation.certificate_arn` plutôt que par `aws_acm_certificate.arn` est le bon choix : il crée la dépendance de graphe qui empêche CloudFront d'être mis à jour avec un certificat encore `PENDING_VALIDATION`.
- [x] Aucune régression sur le reste du module — `git diff origin/dev...HEAD --name-only` renvoie exactement `acm.tf` et `s3_back-office.tf` ; `git diff origin/dev...HEAD -- s3_app.tf s3_assets.tf providers.tf` renvoie 0 ligne.
- [x] `terraform validate` passe sur les deux environnements — reproduit indépendamment avec le Terraform 1.15.6 pinné par `environments/<env>/terraform.<env>.json`, module copié avec `variables.stg.tf` puis `variables.prd.tf`, `backend "s3" {}` neutralisé pour permettre un `init` hors ligne : `Success! The configuration is valid.` pour stg et pour prd. Le `plan`/`apply` réel n'a pas été exécuté (aucun credential AWS disponible dans cet environnement).
- [x] L'URL `*.cloudfront.net` existante survit à la bascule de certificat — vrai pour tout client SNI, c'est-à-dire tout navigateur et tout outil moderne. CloudFront choisit le certificat d'après le SNI : une requête présentant `d2w680tajopann.cloudfront.net` continue de recevoir le certificat `*.cloudfront.net` par défaut. Corroboré par la section *Domain fronting* de [CNAMEs.html](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/CNAMEs.html) : « If the client doesn't provide the SNI extension and gets a default \*.cloudfront.net certificate instead, CloudFront will accept the incoming requests », et par « CloudFront identifies a distribution for an HTTP request based on the `Host` header. CloudFront doesn't depend on [...] what SNI handshake was provided ». Le chemin de déploiement est lui aussi insensible au changement : `infrastructure/scripts/deploy.react.py:153` invalide par un ID de distribution figé dans `environments/<env>/deploy.<env>.json`, jamais par domaine, et la CORS de l'API est `allow_origins = ["*"]` (`infrastructure/terraform/api/apigateway.tf:10`). Réserve documentée, voir finding 🟢 `fit` : les clients **sans** SNI, eux, passent de « fonctionne » à « connexion coupée ».
