| 🟡 | code | 1 | `.github/workflows/migrate-stg-on-demand.yml:9` | Aucun garde `concurrency:`. | 🟡 | fit | 1 | `aidd_docs/memory/infra.md:35` et `.github/workflows/migrate-stg-on-demand.yml:5-8` | La justification de sécurité écrite surestime le confinement du token : « a leaked token can only ever re-run this one job, never anything else in the shared pipeline ». `Actions: write` est une permission **repo-wide**, GitHub n'offre aucun scoping par fichier workflow. Le fichier séparé borne ce qui est *dispatchable* (vérifié : `ci-cd.yml:3-11` n'a que `push`/`pull_request`, aucun `workflow_dispatch`, et ce sont les 2 seuls workflows du repo), pas ce que le token peut faire. Avec `Actions: write` seul, un token fuité peut aussi `POST /actions/runs/{id}/rerun` (y compris un run prd déjà exécuté : re-apply Terraform prd, redeploy prd), `POST /actions/runs/{id}/cancel` (déni de déploiement), `DELETE /actions/runs/{id}/logs` (effacement de piste d'audit), et supprimer artifacts et caches. Ce qu'il ne peut PAS faire, et c'est ce qui valide la décision face à l'alternative écartée : lire un secret, modifier le code exécuté par un re-run, ni toucher directement aux données prd — là où des credentials DB master sur un Lambda public donnent un accès direct en lecture/écriture/DDL. | Corriger la phrase plutôt que l'architecture : le choix reste le bon. Remplacer « can only ever re-run this one job » par le périmètre réel (dispatch borné à ce job ; re-run/cancel/suppression de logs possibles sur les runs existants ; aucun accès aux secrets ni aux données). Et poser les deux contre-mesures qui en découlent : expiration courte + rotation du token, et vérifier que le repo n'acquiert jamais un second workflow `workflow_dispatch` sans réévaluer ce raisonnement. |
